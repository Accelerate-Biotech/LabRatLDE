# SPEC-002: Sealing completeness

| | |
|---|---|
| **Status** | Approved |
| **Owner** | Rob Bassett |
| **Created / Updated** | 2026-10-18 / 2026-10-18 |
| **Regulatory refs** | 21 CFR 11.10(c), 11.10(e), 11.70 |
| **Depends on** | `SPEC-001` |

## 1. Problem

When a run is signed, the scaffold freezes the `runs` row and nothing else. The database still accepts new inputs linked into the signed run, new datasets attributed to it, more readings appended to its datasets, and direct `UPDATE`s of lineage node attributes. A reviewer or auditor therefore can't trust that what was signed is still what the record shows. Separately, the application role holds `UPDATE` on tables that no endpoint updates, which leaves a mutation path that nothing audits.

## 2. Scope

**In scope**
- Define the **sealed set** of a signed run: the run's lineage node plus every dataset node generated by the run.
- Database rules that stop the sealed set gaining inputs or outputs, having its readings appended to, or having its node rows changed.
- Readings for a dataset can only be written by the transaction that created that dataset.
- Revoke `UPDATE` grants that no endpoint uses.

**Out of scope**
- Correcting a sealed record. That arrives through reviewed change sets (SPEC-007, SPEC-008).
- Sealing aborted or failed runs (see open question 1).
- Changing the definition of "signed". SPEC-008 widens the sealed predicate to "has at least one valid signature" and supersedes R01's trigger condition.

## 3. Simplicity budget

- Approach: one SQL function, `lineage_node_sealed(node_id)`, used by `BEFORE` triggers on `lineage_edges`, `lineage_nodes` and `instrument_readings`, all added in one new migration. Grant changes go in the same migration.
- Not doing: a generic "lock" table, application-level checks only, or a seal flag column that would have to be kept in sync.

## 4. Requirements (EARS)

| ID | Requirement | Test | Source |
|---|---|---|---|
| SPEC-002-R01 | The database shall treat a lineage node as sealed when it is the node of a run in state `signed`, or is the target of a `wasGeneratedBy` edge from such a run node. | yes | 11.10(c) |
| SPEC-002-R02 | If a lineage edge is inserted whose `to_id` is a sealed node, then the database shall reject it with SQLSTATE `LDE04`. | yes | 11.10(c), 11.70 |
| SPEC-002-R03 | If a lineage edge with relation `wasGeneratedBy` is inserted whose `from_id` is a sealed run node, then the database shall reject it with SQLSTATE `LDE04`. | yes | 11.10(c) |
| SPEC-002-R04 | The database shall continue to accept edges whose `from_id` is a sealed node with relations other than `wasGeneratedBy`, so later work can use sealed outputs. | yes | data integrity |
| SPEC-002-R05 | If a sealed lineage node is updated or deleted, then the database shall reject the statement with SQLSTATE `LDE04`. | yes | 11.10(c) |
| SPEC-002-R06 | If instrument readings are inserted for a sealed dataset, then the database shall reject the insert with SQLSTATE `LDE04`. | yes | chain of custody |
| SPEC-002-R07 | If instrument readings are inserted for a dataset in a transaction other than the one that created the dataset node, then the database shall reject the insert with SQLSTATE `LDE04`. | yes | chain of custody (SPEC-001-R13) |
| SPEC-002-R08 | The database shall not grant the application role `UPDATE` on `experiments`, `lineage_nodes` or `instruments`. | yes | 11.10(e) |
| SPEC-002-R09 | When the database rejects a statement with SQLSTATE `LDE04`, the API shall respond `409 Conflict` with a message naming the sealed entity. | no | usability |

## 5. Acceptance examples

Shared fixture: sample `S` →used→ run `R` →wasGeneratedBy→ dataset `D` (100 readings, ingested by instrument `I`). `R` goes planned→running→completed→signed("approved").

**SPEC-002-R01**
- Given the fixture, `lineage_node_sealed` is true for `R` and `D`, and false for `S` and `I`.
- Given the same fixture but `R` only `completed`, it is false for `R` and `D`.

**SPEC-002-R02**: inserting reagent `X` →used→ `R` fails with `LDE04`. Inserting new node `Z` →wasDerivedFrom→ `D` (that is, `to_id = D`) fails with `LDE04`.

**SPEC-002-R03**: inserting `R` →wasGeneratedBy→ new dataset `D2` fails with `LDE04`.

**SPEC-002-R04**: inserting `D` →used→ new analysis node `A` succeeds.

**SPEC-002-R05**: `UPDATE lineage_nodes SET attrs = '{"x":1}' WHERE id = D`, run as the table owner, fails with `LDE04`. The same statement for `S` succeeds as owner.

**SPEC-002-R06**: inserting one reading for `D`, as the owner, fails with `LDE04`.

**SPEC-002-R07**: with `R` still `running`, create dataset `D3` with 1 reading and commit. A second transaction inserting another reading for `D3` fails with `LDE04`.

**SPEC-002-R08**: as `lde_app`, `UPDATE experiments`, `UPDATE lineage_nodes` and `UPDATE instruments` each fail with `insufficient_privilege`. `UPDATE runs` still succeeds for an unsigned run.

## 6. Data and interfaces

- New migration: `lineage_node_sealed(uuid) RETURNS boolean` (`STABLE`), triggers `lineage_edges_sealed`, `lineage_nodes_sealed` and `instrument_readings_sealed`, plus `REVOKE UPDATE ON experiments, lineage_nodes, instruments FROM lde_app`.
- R07 mechanism (implementer's choice, documented in the migration): e.g. compare the dataset node row's `xmin` with `pg_current_xact_id()`, or keep a transaction-local set of datasets created in this transaction.
- New SQLSTATE `LDE04` = "sealed record". `storage` maps it to a conflict.
- No new endpoints and no new audit actions.
