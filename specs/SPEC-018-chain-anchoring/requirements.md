## 1. Problem

The audit chain proves integrity relative to a known head (`docs/audit-chain.md`, threat model). Someone with superuser access could disable the triggers and rewrite the whole chain consistently, and nothing inside the database would notice. The defence is to record chain heads *outside* LabRat's control, regularly and in a way that can be verified independently. Then a silent rewrite becomes a detectable one.

## 2. Scope

**In scope**
- Periodic and on-demand **checkpoints**: tenant, seq, head hash and time, signed with a server Ed25519 key.
- Checkpoints are stored append-only and also written to external sinks: an append-only file in `LDE_CHECKPOINT_DIR` (e.g. a WORM mount) and a structured log line.
- An optional **RFC 3161** timestamp token from a configured TSA.
- Public key publication.
- Verification: the engine and `tools/verify_audit.py` check a chain against a set of checkpoints.
- Key generation with `labrat keygen`.
- A new non-normative doc, `docs/audit-checkpoints.md`.

**Out of scope**
- Any change to the v1 digest or to `docs/audit-chain.md` v1 (frozen).
- Public transparency logs such as Sigstore Rekor (open question 2).
- Key rotation policy and HSM support (open question 1).

## 3. Requirements (EARS)

| ID | Requirement | Test | Source |
|---|---|---|---|
| SPEC-018-R01 | When a checkpoint is taken, the anchoring service shall sign the line `LDE-CHECKPOINT-v1 <tenant> <seq> <hash-hex> <unix-micros>` with the server's Ed25519 key and store tenant, seq, hash, time, signature and key id. | yes | 11.10(e) |
| SPEC-018-R02 | If any role attempts to update or delete a checkpoint, then the database shall reject the statement with SQLSTATE `LDE03`. | yes | 11.10(c) |
| SPEC-018-R03 | When a checkpoint is stored, the anchoring service shall also append it as one JSON line to `LDE_CHECKPOINT_DIR/<tenant>.ndjson` and emit it as a structured log record. | no | external evidence |
| SPEC-018-R04 | While the server runs, the anchoring service shall take a checkpoint for each tenant whose chain head has advanced, every `LDE_CHECKPOINT_INTERVAL` (default 1 h). | no | operations |
| SPEC-018-R05 | Where `LDE_TSA_URL` is set, the anchoring service shall obtain an RFC 3161 timestamp over the checkpoint line and store the token with the checkpoint. | no | trusted time |
| SPEC-018-R06 | When a chain is verified against checkpoints, the verifier shall report a failure if, for any checkpoint, the chain's event at that seq doesn't exist or its hash differs from the checkpoint's hash. | yes | 11.10(c), (e) |
| SPEC-018-R07 | When a checkpoint's signature is verified with the published public key, verification shall fail if any field of the checkpoint line differs. | yes | 11.10(e) |
| SPEC-018-R08 | The API shall publish the current and past checkpoint public keys with their key ids at `GET /v1/audit/checkpoint-keys`. | no | verifiability |
| SPEC-018-R09 | If `LDE_ENV=prod` and no checkpoint key is configured, then the server shall refuse to start. | no | secure default |

## 4. Acceptance examples

Fixture: tenant `T1` with 10 audit events, a key pair generated by `labrat keygen`, and a checkpoint at seq 10.

**SPEC-018-R01 / R07**: the stored signature verifies against the line built from the stored fields and the public key. Changing seq to 9 or flipping one bit in the hash makes verification fail.

**SPEC-018-R02**: `UPDATE audit_checkpoints SET seq = 9` and `DELETE`, as the owner, each fail with `LDE03`.

**SPEC-018-R06**: a superuser disables the triggers, rewrites events 5–10 consistently (the chain still verifies on its own), and re-enables them. Verifying against the checkpoint file then reports a failure at checkpoint seq 10. `python3 tools/verify_audit.py chain.ndjson --checkpoints T1.ndjson` exits non-zero too.
